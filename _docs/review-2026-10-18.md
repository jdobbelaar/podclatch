# Review of the project plan (2026-10-18)

A record of the review requested in the initial instructions: how the course scoring criteria fit the app, feedback on the guiding documents, and whether the class's phased approach fits. Decisions made afterward are marked **Decided**. The per-criterion plan lives in `full-score-criteria.md`; this file keeps the reasoning.

## 1. Scoring criteria

The class page confirms 12 criteria worth 24 points (CI/CD is 3, Alerting is 1, the other ten are 2 each). Passing needs 10. The class also requires peer-reviewing three other projects; skipping that fails the project regardless of its score.

| Criterion | Pts | Without a backend | With a backend |
|---|---|---|---|
| Problem description | 2 | Met once the README is finished | Same |
| Spec and tracker | 2 | Met | Same |
| Agent team | 2 | Met | Same |
| Context management | 2 | Met | Same |
| Application | 2 | 0, because a missing backend or database scores 0 | Met |
| Testing | 2 | Met | Met |
| Containerization | 2 | Weak, nothing to run in Compose | Met |
| Deployment | 2 | Possible with an APK and demo | Met, with a public URL |
| CI/CD | 3 | About 2 | 3 |
| Observability | 2 | Not applicable | Met |
| Alerting | 1 | Not applicable | Met |
| On-call agent | 2 | Not applicable | Met |

Without a backend the ceiling was roughly 14-15 points, with little margin over the pass mark.

**Decided:** add **PodClatch Server** (FastAPI and Postgres, one static token). It proxies iTunes search, fetches and parses feeds, refreshes them on a schedule, and stores subscriptions, Feed Priority, Listen Order, and per-episode state, which it syncs to the phone. The phone keeps a Room cache for offline use and downloads audio directly from publishers. To offset the added scope, OPML import/export (US-19) and the Storage screen (US-18) were deferred.

### Findings that changed the plan

- **The Android emulator cannot run inside Docker for reviewers.** It needs KVM, which means a Linux host; Docker Desktop on Windows and Mac does not provide it. The "single command" is therefore `make up` for the server stack plus `./gradlew installDebug` for the app. CI runs the emulator-based tests on a Linux GitHub runner, and a demo plus a downloadable APK covers the phone side.
- **"Public URL" applies to the server**, through its health endpoint.
- **Integration tests** are: server tests against the Compose stack with a fake feed host, and an end-to-end test driving the app on an emulator against that stack.
- **Observability:** the app sends a W3C `traceparent` header so one trace spans app and server. Feed URLs can embed private tokens, so they must never reach telemetry.
- **On-call agent:** an alert webhook triggers a GitHub Actions workflow that runs Claude Code headlessly and opens a fix PR; a human merges. It is demonstrated with a seeded fault.

### Things only the human can do

See "Your setup list" in `full-score-criteria.md` (AWS account, MFA, budget alert, CLI, GitHub environments, secrets, Android Studio), plus: make the repository public before submission after checking its history for secrets, and complete the three peer reviews on the course platform.

## 2. Feedback on the guiding documents

**`AGENTS.md`** (applied, DRAFT banner kept): the Python commands and `pyproject.toml` rule did not fit an Android project; it now covers both parts, with the layout, commands, rules, and document pointers. The dangling pointers to nonexistent docs were removed.

**`process.md`** (applied, DRAFT banner kept):
- Five parallel agents was too many for Android: each worktree needs a heavy Gradle build, agents cannot share an emulator, and the Room schema, Hilt modules, navigation graph, version catalog, and `openapi.yaml` are conflict hot spots. It is now three agents, with emulator and shared-file rules.
- Added a setup step that creates milestones and issues, a pull-request and CI step before merging, a three-round limit on QA failures, a route back to the PM when a criterion is wrong, required comments from every role as tracker evidence, a stop at the end of each milestone, and human checkpoints.

**Role docs** (applied): the PM links spec sections, names the area and files, flags changes to the API, and marks human-only checks `[manual]`. The engineer uses branches and PRs, runs the area's tests, and follows contract-first. QA's examples and test layers are Android and server specific, it checks CI, and it reports `[manual]` checks with steps rather than guessing.

## 3. Is the class's phased model right for this app?

Yes, now that there is a server. The class's order was: frontend against a mock, then an OpenAPI contract, then the backend with a mock store, then a real database, then containers, then integration and end-to-end tests, then cloud and CI/CD.

**Decided:** the spec follows that shape with two changes. The contract comes first (M1), because the spec already defines the behavior, and the server is built before the Android screens so the app is written against a real, tested server. Milestones are M0 setup, M1 contract, M2 server core, M3 server persistence and containers, M4-M8 the Android work, M9 delivery (end-to-end test, AWS, CI/CD, demo), and M10 observability, alerting, and the on-call agent.

**One kickoff or many?** Define the documents once. Create all milestones and issues up front, but start the orchestrator once per milestone ("work milestone Mx until it is empty, then stop and report"). State lives in GitHub issues, so a restarted session loses nothing, and grooming happens just before each issue is worked. The human approves a few things between milestones: AWS spending, secrets, emulator-only checks, and the production deploy.

## 4. Will the app always need the server?

As specified, yes. Search, subscribe, reorder, Listen Order, and Refresh all live on the server. If the server went away, the app would keep playing what it had already synced and downloaded, but it could not discover or add anything new.

Options after the evaluation:
1. **Keep the server, make it cheap.** Tear down the AWS stack and run the same Docker Compose setup (SQLite or Postgres) on a home machine or a small VPS. No code changes.
2. **Build standalone mode.** All server access goes through one `PodClatchApi` interface used only by repositories (spec decision 9), so a second implementation that does iTunes search and RSS parsing on the device could replace it. It is listed in spec section 9 as a future idea; the work is mostly the RSS parsing and refresh logic the original spec already described.

Option 1 is the practical path; option 2 is the way to drop the server entirely.
